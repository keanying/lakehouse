## 架构与分层

### A1【高】三个工作空间各自建了一套数仓，没有统一的分层

「数据中台」「数据平台」「业务工厂」三个空间都在做 ODS→ADS：数据中台有 ODS / 原始数据层(ODS)、DIM / 数据维度(DIM)、DW / 数仓明细层(DWD) 两套同义目录；数据平台按 SRC/ODS/DIM/DWD/DWS/ADS 分层；业务工厂按业务主题（景区指标、商户数据中心、报表数据、内部信息…）建目录，每个主题从同步到出数自成一套。三个空间之间互相读表 360 处。

**建议**：以 PFT3.0 的分层为准收敛成一个数仓空间：ODS 每张业务表只落一次，DWD/DIM/DWS 按业务过程与主题建公共层，业务工厂只保留 ADS 与回流任务。

明细：`output/A1.csv`（17 行）

### A2【高】ADS / DWS 直接读 ODS，公共明细层形同虚设

59 张 ADS、25 张 DWS 跳过 DWD 直接从 ODS 取数，同一套清洗（去重、状态过滤、金额换算）在每张报表里各写一遍；另有 10 处反向引用（如 DIM 读 DWS、ODS 读 DIM）。

**建议**：ODS → DWD 只做一次清洗；DWS/ADS 一律从 DWD/DWS 取数；DIM 不依赖汇总层。

明细：`output/A2.csv`（205 行）

### A3【中】表命名多套规则并存

703 张 Hive 表：后缀 _d_i / _d_f 487 张、_di / _df 169 张、无后缀 47 张；分层前缀之外还有 9 张用 cache_, tmp_, temp_ 等前缀；同一业务表的 ODS 有 s_xxx / ods_xxx / src_xxx / ods_myuu_xxx 多种叫法。

**建议**：统一按《数仓命名规范》：层_域_实体_粒度后缀（_di/_df/_zip/_f），存量表建映射表逐步改名。

明细：`output/A3.csv`（703 行）

### A4【中】业务库分表按月 / 按年各同步一张 ODS

业务库的分表（如订单 201801…202501）在 ODS 各落一张（46 张），下游要 UNION 才能用，新增分表要改任务。

**建议**：ODS 按逻辑表合并（同步任务多表读取写同一张表，带分表来源列）。

明细：`output/A4.csv`（46 行）

### G2【中】数仓被当作业务库之间的搬运通道

0 个任务把 OA、CRM 等业务库直接搬到 Oracle（RDS_oracle / RDS_oracle_it_project，不经过数仓）；149 个任务每天把 Hive 结果全量写回 MySQL / Oracle / SelectDB / ClickHouse 给报表用。回流目标表也有 daily_* / _new / _bak2 多版本。

**建议**：系统间同步与数仓分开管理；报表统一从数仓的服务层（StarRocks / SelectDB）读，减少回流份数。

## 重复开发

### B1【高】同一张业务表被多个任务重复同步

30 张业务表被 81 个同步任务重复抽取。最严重的订单主表 POLAR_myuu.uu_ss_order 被 6 个任务、分布在 3 个工作空间抽取（s_order_d_i、s_order_update_d_i、ods_myuu_uu_ss_order_di、src_uu_ss_order_di…），每天对业务库重复全量 / 增量读取。

**建议**：一张业务表只保留一个 ODS 同步任务（增量 + 合并），其他任务改读这张 ODS。

明细：`output/B1.csv`（30 行）

### B2【中】同一个业务库配置了多个数据源名

3 张表从不同名字的数据源读取（如 RDS_pft_open_cooperate / BI_RDS_pft_open_cooperate、RDS_oa_ecology / BI_RDS_oa_ecology、RDS_summary / BI_RDS_summary），同一个库两套账号与连接，重复同步不易发现。

**建议**：每个业务库只保留一个数据源，按库命名。

明细：`output/B2.csv`（3 行）

### B3【高】同一张表由多个任务写入

13 张 Hive 表有多个写入任务且写同一批分区：如 ods_pft_report_checked_two_d_i 被正式工作流、归档抽取工作流和「手动任务_动态分区」3 个节点写入；ads_data_center_report_order_summary_d_i 的初始化节点（_o_f）仍在每天调度；ads_trf_scenic_passenger_flow_di 在数据平台和业务工厂各有一套；归档库按 2022–2025 年拆成 4 个节点写同一张表。后跑的任务会覆盖先跑的结果。（另有 3 张表多个任务各写各的分区，如增量登记表 dim_src_table_increment_info_di、按 data_domain 分区合并的 ads_digital_brain_target_merge_di，属设计如此，未计入。）

**建议**：一张表只能有一个生产任务；补数用同一任务的补数据功能，不复制节点。

明细：`output/B3.csv`（13 行）

### B4【高】订单明细被反复加工成多张口径不一的 DWD

从订单主表 uu_ss_order 往下共 310 张表，其中订单类 DWD 有 24 张（dwd_order_d_i、dwd_split_d_i、dwd_order_split_d_i、dwd_ord_order_details_di、dwd_order_d_f_v7、dwd_order_verify_d_i_v8…），各自定义了订单状态、拆单、核销口径，下游报表取哪张由开发者决定，数字对不上。

**建议**：订单域只保留 PFT3.0 的 DWD：下单 / 支付 / 核销 / 退款四个业务过程各一张，拆单、游客、轨迹作为子表或宽表字段。

明细：`output/B4.csv`（24 行）

### B5【高】「景区指标旧表」与「景区指标宽表」两套同时在跑

旧表 116 个节点（111 张表，按 渠道 × 省份 × 团散 × 票种… 每种组合一张）与宽表 57 个节点（48 张表）都在正常调度、都回流到 RDS_bi_datav；旧表基于 dwd_split_d_i，宽表基于 dwd_order_d_i / dwd_order_track_d_i，两套口径并行，前端看到的数可能来自任一套。

**建议**：确认前端已全部切到宽表后，暂停旧表并保留一个账期对数，再下线。

明细：`output/B5.csv`（173 行）

### B6【中】大量 _new / _bak2 / _v7 / _temp 版本表在生产

16 张表带版本或临时后缀（daily_*_new、monthly_*_bak2、dwd_order_d_f_v7、dwd_order_verify_d_i_v8、s_*_temp…），新旧版本同时被调度和回流，不清楚哪张在用。

**建议**：每个版本表确认使用方后保留一张、改回正式名，其余停调度后删除。

明细：`output/B6.csv`（16 行）

### B7【中】测试 / 副本节点在生产调度

11 个节点名带 test / copy / _err / _dev 等（如 dim_date_isoweek_o_f_copy、test_emr_spark、ods_micromessage_page_view_d_f_err、oa_to_oracle_*_copy），全部在周期调度。

**建议**：测试放开发空间；副本节点删除。

明细：`output/B7.csv`（11 行）

## 指标冗余

### C1【高】同一个指标在几十张表里各算一遍

86 个指标字段在 5 张以上 ADS/DWS 里重复计算：order_num 出现在 22 张表、ticket_num 9 张、paid_amount 18 张、verify_ticket_num 2 张……每张表自己从明细聚合，口径（是否含退票、取消、测试单）各写各的。

**建议**：按 PFT3.0 的口径字典把每个指标登记一次、在 DWS 落一次，ADS 只引用 DWS，不再从明细重算。

明细：`output/C1.csv`（86 行）

### C2【中】同一指标多种字段名

指标类字段共 1422 个名字，同义词并存：订单数：order_num / ordernum / ordernum_num / paid_count；票数：ticket_num / mo_ticket_count / verify_num；金额：paid_amount / payment_money / sale_money / mo_amount / total。下游无法判断是否同口径。

**建议**：建立指标字典（编码、标准名、口径、单位），字段名统一按字典。

明细：`output/C2.csv`（3 行）

### C3【高】按日 / 月 / 年各建一套报表表

34 组报表按 daily_* / monthly_* / yearly_* 各建一张（加上 _new、_bak2 版本），每组 2–3 套 SQL 分别从明细聚合；新增一个周期（季度、节假日、自定义区间）就要再复制一套。这与 PFT3.0 改造前 ADS 的问题相同。

**建议**：按 PFT3.0 方案：ADS 只存日粒度，周 / 月 / 年 / 节假日 / 自定义区间在查询时关联统计周期时间表汇总。

明细：`output/C3.csv`（34 行）

## 性能

### D1【高】同步任务大量每天全量

506 个同步任务中 344 个没有增量条件：从业务库全量抽 195 个（其中订单 / 流水 / 日志类大表 39 个），从 Hive 全量回写 MySQL / Oracle 149 个。数据量随时间线性增长，同步窗口和业务库压力越来越大。

**建议**：业务库按 update_time 增量 + ODS 合并；回流只推当天分区（按分区覆盖 / upsert）。

明细：`output/D1.csv`（344 行）

### D3【中】SQL 写法问题

SELECT * 55 个；COUNT(DISTINCT) 28 个；写入前 ORDER BY 27 个；写死日期 12 个；CROSS JOIN 8 个；NOT IN 子查询 7 个；UNION（去重） 6 个。

**建议**：列裁剪、去掉写入前排序、UNION ALL、NOT EXISTS / LEFT ANTI JOIN、日期用调度参数。

明细：`output/D3.csv`（143 行）

### D4【中】超长脚本与深层子查询

42 个脚本嵌套子查询 ≥10 层（dwd_order_split_d_i 44 个），36 个脚本超过 300 行（最长 7,690 行），只有 29 个用了 WITH 分步。难以优化与排错。

**建议**：按 PFT3.0 加工逻辑的写法：WITH 命名逻辑块分步，先过滤分区再关联，多来源先预聚合再 UNION ALL。

明细：`output/D4.csv`（55 行）

### D5【中】没有分区参数的脚本每次全量重算

21 个 SQL 节点不带任何日期参数，每天全表扫描、全量重写（多为 _d_f 汇总与 DIM）。

**建议**：可增量的改为按分区增量；确需全量的降为周 / 月调度或改为拉链。

明细：`output/D5.csv`（21 行）

## 数据质量

### D2【高】增量同步只按创建时间取，漏掉后续变更

23 个增量任务只按 create_time 取当天新增（如订单取票人表），订单后续的支付、取消、退款、核销状态变化不会进入 ODS；于是又另建 s_order_update_d_i 等任务补变更，或干脆每天回溯 15 天（ods_order_apply_15d_i、s_order_fx_details_15d_i）。

**建议**：按 update_time 增量，ODS 用主键合并（_di 增量 + _df 全量快照）。

明细：`output/D2.csv`（23 行）

### D6【中】业务数据写死在 SQL 里，生产表混入演示数据

12 个脚本把景区、商户、会员 ID 名单写死在 WHERE 里（新增景区要改代码）；1 个节点把真实景区的指标复制成虚构景区 PFTSCM00000001「A级景区」写进生产 ADS（ads_digital_brain_target_merge_di），对外接口会读到演示数据。

**建议**：名单放配置维表（已有 dim_sid_white_list_d_f 可复用）；演示数据放独立的演示库或打标后由接口过滤。

明细：`output/D6.csv`（13 行）

## 调度与依赖

### E1【高】读了上游表却没配调度依赖，靠时间差碰运气

127 个节点的 282 处读表在依赖链上找不到产出任务（其中跨工作空间 132 处）。上游延迟或失败时，下游照常运行，读到前一天或空分区，报表静默出错。

**建议**：读谁就依赖谁：跨空间用跨项目依赖或统一到一个空间；上线前用血缘自动校验依赖。

明细：`output/E1.csv`（282 行）

### E2【中】调度扎堆在凌晨

55 个工作流和 366 个独立节点中，406 个（96%）在 0–6 点启动，其中 5 个正好是 00:00:00；业务库全量抽取与 Spark 计算同时挤在凌晨，资源与业务库压力峰值叠加，一个任务慢就整体顺延。

**建议**：同步按业务库错峰（备库 / 低峰时段），计算按依赖自然触发，不靠固定时刻。

明细：`output/E2.csv`（5 行）

### E3【中】所有节点都没有设置超时

969 个节点 / 工作流超时时间全部为 0（不限），卡住的任务会一直占用资源、阻塞下游，不会告警。

**建议**：按历史运行时长设置超时（如 P95 × 2）并配超时告警。

### E4【中】「手动任务」目录里的节点其实在周期调度

业务工厂/手动任务 下 0 个节点（历史重跑、按年份归档、全量导出脚本、动态分区…）全部是周期调度节点，其中不少与正式任务写同一张表（见 B3），每天重复执行一次性的补数逻辑。

**建议**：一次性任务改为手动业务流程 / 补数据；确需周期执行的并入正式工作流。

### E5【低】EMR 与 Serverless Spark 两套引擎混用

EMR_SPARK_SQL 294 个、SERVERLESS_SPARK_SQL 99 个、SERVERLESS_PYSPARK 1 个、EMR_PYSPARK 1 个；同一业务链路上下游跑在不同引擎，资源与参数各管一套。

**建议**：统一一种计算引擎与资源组。

明细：`output/E5.csv`（4 行）

**建议**：对照查询日志确认无访问后停调度，30 天后删表。

明细：`output/F1.csv`（121 行）

### F2【中】读了导出包里没有产出任务的表

51 张被读取的表在三个空间里都没有产出任务（如 cache_table、result_table、dim_distribute_ota_o_f、phone_area），来源不明，可能是手工建表或其他系统写入。

**建议**：补登记来源与负责人，或改为由调度任务产出。

明细：`output/F2.csv`（51 行）

### F3【低】历史分区无限保留，三成表没有表说明

346 个建表语句中 226 个（65%）写了表注释，字段注释覆盖较好；设置生命周期 / 分区保留的只有 7 个，ODS 增量、临时表、_bak2 版本表的历史分区一直保留。

**建议**：表注释、负责人、生命周期纳入上线检查；ODS 增量按需保留，临时表 7 天。

## 安全

### G1【高】手机号、证件号、密码字段原样同步进数仓并回流

81 个同步任务把 ordertel / personid / id_card / mobile / address / card_no 等敏感字段明文落到 Hive；其中 1 个任务连 password 字段一起同步（OA 人员表、CRM 人员表、年卡表），并回写到 Oracle。

**建议**：ODS 落地即脱敏 / 加密（手机号、证件号哈希 + 掩码），密码类字段不同步；敏感表单独授权。

明细：`output/G1.csv`（81 行）
