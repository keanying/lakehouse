# 客户现有 DataWorks 梳理

客户在 DataWorks 上的全部任务（仓库根目录 `DATAWORKS.zip`，三个工作空间：数据中台 / 数据平台 / 业务工厂）。目标：从 ODS 到 ADS 治理，并与 PFT3.0 数仓（`dw-dict/`）对齐、同步维护。

## 运行

现状诊断（问题清单）：

```bash
python3 dataworks/audit.py
```

标准化数仓字典与页面（需要 openpyxl；会复用 `dw-dict/` 的核对规则、ADS 指标体系与页面模板）：

```bash
python3 dataworks/standard/build.py
```

都是直接读 zip，不需要解压。

## 标准化数仓（dataworks/dist/）

按 PFT3.0 同一套标准把旧系统重构为一个数仓，打开 `dataworks/dist/index.html` 查看（页面结构与 3.0 字典页相同，多一个「旧系统对照」）：

| 层 | 表数 | 做法 |
|---|---|---|
| 业务库 | 368 | DataWorks 同步任务读取的全部业务表（含只直传 Oracle、不进数仓的） |
| ODS | 290 | 一张业务表只落一次：367 个物理同步合并为逻辑表（月 / 年分表、历史库、BI_ 数据源别名合并），敏感字段落地脱敏、密码类字段不同步 |
| DIM | 24 | 景区、产品、门票、价格拉链、供应商、会员、游客、统一用户、分销关系、CRM 客户、合同、员工、渠道、支付方式、闸机、地区、号段、证件地区、模块套餐、码表；日期表、节假日表、统计周期时间表与 PFT3.0 共用（字段直接从 3.0 字典同步） |
| DWD | 17 | 按业务过程：订单、分销链、订单操作、核销、游客、年卡、出入园、停车、零售、账户流水、登录、模块开通、资源中心订单、页面访问、合同事件、客户拜访、服务商户；订单域 5 张表逐字段给出替代的旧字段名 |
| DWS | 15 | 主题 × 粒度日汇总，64 个口径只在这里算一次（预订 / 支付 / 取消 / 验证 / 完结 / 撤销 / 取票 × 订单数 / 票数 / 金额 / 成本 等）；旧系统 28 个性别 × 年龄透视列改为维度行 |
| ADS | 18 | 日粒度；周 / 月 / 年 / 节假日 / 自定义在查询时关联时间表（与 3.0 相同），旧系统 daily / monthly / yearly 三套报表合一 |

- `旧版数仓_标准化字典.xlsx`：与 3.0 字典相同的工作表（分层汇总、表清单、字段清单、调度工作流、质量规则、DWS口径、ADS业务指标、总线矩阵、质量体检、待确认事项），另加「旧表映射」「现状问题」；
- 旧表映射：875 张 Hive 表 + 420 张回流表逐张给出标准表与处理方式（合并 / 改名 / 回流改造 / 移出数仓 / 下线 / 项目专用）；
- 表详情「加工逻辑」：每张标准表可上线的实现（同时落盘到 `dataworks/sql/<层>/`，见 `sql/README.md`），头部注释写明粒度、上游、替代的旧任务、业务规则与修正、性能做法；旧任务原脚本折叠在下方，仅供对数：
  - ODS 290 张：数据集成脚本模式 JSON，按 `update_time` 增量、列裁剪、分表多表读取、历史库只初始化一次、读端脱敏（手机号 / 证件号保留前缀 + SHA256）；
  - 实体维度与订单域（`standard/etl_core.py` 手写）：沿用旧系统真实规则（单价置零、原始票数 = 下单 + 加票、验证票数取法、客源地优先级），修正旧 bug；订单只重算有变更的下单日分区，操作 / 核销明细关联订单时带下单日分区（动态分区裁剪），订单属性在 DWD 一次带齐；
  - 其余 DIM / DWD：按字段映射生成，停车 5 厂商、零售 3 系统 UNION ALL 归一；旧宽表（字段散在多张中间表）过渡期从旧表平移；
  - DWS 由指标口径生成：每个指标 = 来源 + 条件 + 聚合，同一来源预聚合一次、各来源 UNION ALL 后汇总，去重类存位图；ADS 日粒度从 DWS 再汇总；
  - 每段 SQL 经 sqlglot 解析并核对输出列与字段清单一致；无来源的字段标「待确认」（ODS 0、DIM 102、DWD 73、DWS 8、ADS 0）；
- 设计在 `standard/model.py`（表、粒度、字段、口径、旧表归并规则）与 `standard/rules.py`（业务域、ODS 命名、字段名标准化），改设计改这两个文件后重跑即可。

## 排除范围

`exclude.txt` 列出不纳入梳理的旧节点路径（目前：`数据平台/DWD/dwd_全网舆论`，2 个已废弃节点）。问题诊断、旧表映射、标准化数仓、加工逻辑都会跳过这些节点；导出包本身不改。要再排除目录，加一行后重跑 `audit.py` 与 `standard/build.py`。

## 与 PFT3.0 同步

- 命名规范、分层、业务域、字段关键字、分区字段 travel_date 与 3.0 相同；
- `dim_opr_date_f`、`dim_opr_holiday_period_f`、`dim_opr_period_f` 两边共用，结构从 3.0 字典同步，数据由 `scripts/dim_date/gen_dim_opr_date_f.py` 生成；
- ADS 指标体系（统计周期、派生方式、日粒度存储）、核对规则、页面模板共用 `dw-dict/` 的代码，3.0 改进后重跑本目录即可同步。

## 诊断口径

- **Hive 表**：SQL 节点 `INSERT` / `CREATE TABLE AS` 的目标，以及写端为 Hive 的同步任务目标；写端为 MySQL / Oracle / SelectDB / ClickHouse 的算「回流目标表」。
- **分层**：按表名前缀判断（`ods_` / `s_` / `src_` 记为 ODS，`dwd_`、`dim_`、`dws_`、`ads_`），客户目录名不作依据。
- **缺依赖**：节点读的表在包内有周期产出任务，但该任务不在这个节点的上游依赖链（含间接依赖）里；一次性表（`_o_f` / `_o_i`）与已暂停的产出不计。
- **多任务写同一表**：多个节点写同一批分区才计；按不同静态分区值或按表名 / 数据域等动态分区各写各的（如增量登记表）不计。
- 只看导出包内的任务；包外的查询方（BI、接口、即席查询）需结合访问日志确认，尤其是「没人用的表」。
